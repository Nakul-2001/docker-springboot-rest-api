This guide records the commands and concepts used in the learning exercise. In production, the build and deployment steps are usually automated through CI/CD, and workloads commonly run behind a load balancer or on a managed container platform.

Part 1 — Basic Docker commands and concepts

Docker packages an application and its runtime dependencies into an image. A container is a running instance of that image. Docker helps make the application environment repeatable across a laptop, test server, and cloud server.

1. Docker mental model

Image

A read-only package/template containing the application, runtime, libraries, filesystem and startup configuration.

Example docker-spring-demo:1.0-amd64

Container

A running (or stopped) instance created from an image. It has its own process, filesystem view, network configuration and lifecycle.

Example docker-spring-demo

Other important terms

  • Registry: a service that stores and distributes images. Docker Hub and Amazon ECR are examples.
  • Repository: a named collection of related images in a registry, such as docker-spring-demo.
  • Tag: a human-readable label for an image version, such as 1.0-amd64. Tags can be moved to a different digest when an image is pushed again with the same tag.
  • Digest: a content-derived immutable identifier, typically shown as sha256:....
  • Docker Engine/daemon: the background service that builds images and creates/runs containers. The Docker CLI sends requests to it.
  • Build context: the files Docker is allowed to access during a build. In docker build ... ., the dot means the current directory.
Remember: docker build creates an image; docker run creates and starts a container from an image. An image is not itself a running application.

2. Basic Docker commands we learned

Check images and containers

docker images
docker ps
docker ps -a
CommandPurpose
docker imagesLists images stored locally, with repository, tag, image ID and size.
docker psLists currently running containers.
docker ps -aLists all containers, including stopped and exited ones.

Download and run an image

docker pull nginx
docker run nginx
docker run -d --name my-nginx nginx
  • docker pull downloads an image from a registry to the local machine.
  • docker run creates a new container and starts it. Without -d, it normally attaches the terminal to the container's output.
  • -d means detached mode: the container runs in the background.
  • --name gives the container a stable, readable name instead of a randomly generated one.

Stop, remove and inspect containers

docker stop my-nginx
docker rm my-nginx
docker logs my-nginx
docker logs -f my-nginx
docker logs --tail 50 my-nginx
docker exec -it my-nginx sh
docker inspect my-nginx
docker port my-nginx
CommandWhat it does
docker stopGracefully asks a running container to stop.
docker rmRemoves a stopped container. Stop it first unless using force.
docker logsShows stdout/stderr output from the container's main process.
docker logs -fFollows new log output. Pressing Ctrl+C stops following; it does not stop the container.
docker logs --tail 50Shows only the most recent 50 log lines.
docker exec -it ... shStarts an interactive shell inside a running container. -i keeps input open; -t allocates a terminal.
docker inspectShows detailed configuration and runtime metadata, usually as JSON.
docker portShows published host-to-container port mappings.

Remove images and copy files

docker rmi IMAGE_OR_ID
docker cp ./file.txt my-container:/app/file.txt

docker rmi removes a local image. It may fail if a container still references it. docker cp copies files or directories between the host and a container.

Do not confuse: docker stop stops a container; docker rm deletes the container; docker rmi deletes an image. Removing a container does not automatically remove its image.

3. Dockerfile — how we packaged the Spring Boot JAR

A Dockerfile is a text file containing instructions Docker uses to build an image. Our project Dockerfile was:

# Base image containing Java 17 runtime
FROM eclipse-temurin:17-jre

# Set working directory inside container
WORKDIR /app

# Copy executable Spring Boot JAR into container
COPY target/docker-spring-demo-1.0-SNAPSHOT.jar app.jar

# Document the application port
EXPOSE 8080

# Start the Spring Boot application
ENTRYPOINT ["java", "-jar", "app.jar"]
InstructionExplanation
FROMChooses the base image. eclipse-temurin:17-jre supplies a Java 17 runtime, so the container can execute Java bytecode.
WORKDIR /appSets the working directory inside the image/container. Later relative paths are resolved from this directory.
COPY source destinationCopies the built JAR from the build context on the host into the image as /app/app.jar.
EXPOSE 8080Documents the port the application listens on. It does not publish the port to the host by itself.
ENTRYPOINTDefines the main process to run when the container starts. Here it launches the JAR using Java.

Why use a JRE and not a JDK?

The application was already compiled and packaged into an executable Spring Boot JAR. It needs a JVM/runtime to execute, not a Java compiler. A JDK is needed in a build stage when compiling Java source; a smaller JRE/runtime image is suitable for the final runtime stage.

Why did we add the Spring Boot Maven plugin?

The plugin repackages the application as an executable “fat” or “uber” JAR containing the app and its dependencies. Initially, the plain JAR was only a few KB and did not bundle runtime dependencies. After adding spring-boot-maven-plugin and running Maven package, the executable JAR was roughly 20 MB and could be started using java -jar.

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
  </plugins>
</build>

.dockerignore

We also created .dockerignore in the project root to keep unnecessary files out of the build context:

.git
.gitignore
.idea
*.iml
logs/
temp/
.env

This reduces build-context size and avoids accidentally copying irrelevant local files. It is not a security boundary: never put secrets into an image, and use an appropriate secrets mechanism for builds and runtime configuration.

4. Ports — host vs container

We used the syntax -p HOST_PORT:CONTAINER_PORT.

Mac / EC2 host
port 8081→Container
port 8080→Spring Boot
Tomcat :8080

For local testing, the command was:

docker run -d \
  --name docker-spring-demo \
  -p 8081:8080 \
  docker-spring-demo:1.0

Requests to http://localhost:8081 on the Mac were forwarded to port 8080 inside the container. On EC2 we later used the same mapping, with EC2 host port 8081.

Important: EXPOSE 8080 is documentation/metadata. -p 8081:8080 is what publishes a host port. The left side is the host port; the right side is the port inside the container.

Part 2 — Build, push to Amazon ECR, pull and run on EC2

We used the production-style image distribution flow: build an image, push it to a private registry, then let the server pull and run it. We did each step manually to understand the process.

5. Spring Boot application we deployed

We created a small Java 17 / Spring Boot REST application with a UserController exposing:

HTTP method and pathPurposeExample response
GET /api/usersReturns a list of three sample users.[{"id":1,"name":"Rahul"}, ...]
GET /api/users/{id}Returns a sample user object for the supplied ID.{"id":1,"name":"Rahul"}

We built the executable JAR with Maven and confirmed it worked outside Docker using:

mvn package
java -jar target/docker-spring-demo-1.0-SNAPSHOT.jar

The app listened on port 8080. The JDBC driver/database is a separate concern: a driver library can be packaged in the JAR, but an actual database service is not embedded merely because the application is containerized.

6. Build the image for the EC2 CPU architecture

The Mac was Apple Silicon (arm64) but EC2 reported x86_64. These are different CPU architectures. We therefore explicitly built a Linux AMD64 image so it could run natively on the EC2 host.

cd ~/Downloads/Learning/docker-spring-demo

docker buildx build --platform linux/amd64 --load \
  -t docker-spring-demo:1.0-amd64 .

docker image inspect docker-spring-demo:1.0-amd64 \
  --format '{{.Os}}/{{.Architecture}}'
OptionMeaning
buildx buildUses Docker Buildx, an extended build interface.
--platform linux/amd64Targets Linux on AMD64/Intel/AMD CPUs.
--loadLoads the built image into the local Docker image store so ordinary docker images, tag and push commands can use it.
-t ...:1.0-amd64Gives this architecture-specific image a distinct local name/tag.
.Uses the current directory as the build context.
Why the separate tag? The original local image was docker-spring-demo:1.0. We used docker-spring-demo:1.0-amd64 to make the EC2-targeted build easy to distinguish.

We also had to start Docker Desktop again when the CLI reported it could not connect to the Docker socket. The Docker CLI alone is not enough; the Docker Engine/daemon must be running.

7. Create an ECR repository and push the image

7.1 Verify AWS CLI identity and region on the Mac

aws sts get-caller-identity --profile learning
aws configure get region --profile learning

The learning profile was the IAM CLI profile used for AWS operations, in region ap-south-1 (Mumbai). The AWS account ID returned in this exercise was 404881858086.

7.2 Create the private ECR repository

aws ecr create-repository \
  --repository-name docker-spring-demo \
  --image-scanning-configuration scanOnPush=true \
  --region ap-south-1 \
  --profile learning

ECR (Elastic Container Registry) is AWS's managed container image registry. The repository stores images and makes them available to authorized systems. scanOnPush=true enables image scanning on push for supported vulnerability findings; it does not guarantee an image is vulnerability-free.

7.3 Get the account ID and authenticate Docker to ECR

ACCOUNT_ID=$(aws sts get-caller-identity \
  --query Account --output text --profile learning)

aws ecr get-login-password \
  --region ap-south-1 --profile learning | \
docker login --username AWS --password-stdin \
  $ACCOUNT_ID.dkr.ecr.ap-south-1.amazonaws.com

The first command stores the AWS account ID in a shell variable. The second obtains an ECR authorization password and pipes it directly to docker login. The username is literally AWS. A successful login prints Login Succeeded.

ECR authorization tokens are temporary and normally valid for 12 hours. Authenticate again when needed. Do not paste or store the token in source code.

7.4 Tag the local image with its ECR destination

docker tag docker-spring-demo:1.0-amd64 \
  404881858086.dkr.ecr.ap-south-1.amazonaws.com/docker-spring-demo:1.0-amd64

docker tag adds another name/reference to the same local image. It does not upload or duplicate all the image layers. The full ECR URI identifies the registry, repository and tag.

7.5 Push the image

docker push \
  404881858086.dkr.ecr.ap-south-1.amazonaws.com/docker-spring-demo:1.0-amd64

This uploads image layers and manifest/index metadata to ECR. The output includes layer progress and a digest. This was the actual upload step — repository creation and login did not upload the image.

7.6 Verify what ECR stored

aws ecr list-images \
  --repository-name docker-spring-demo \
  --region ap-south-1 --profile learning

aws ecr describe-images \
  --repository-name docker-spring-demo \
  --region ap-south-1 --profile learning

We saw three ECR records. They were not three separately tagged application releases:

RecordObserved typeMeaning
bceca7a7...OCI image manifest, about 129 MBThe platform-specific image manifest/layers.
31d84663...Docker attestation manifest, about 1.3 KBBuildx provenance/attestation metadata associated with the image, not another runnable application image.
17a54c3a...OCI image index, about 129 MB, tag 1.0-amd64The tagged image index, which points to the image manifest and related metadata.

The important check was that 1.0-amd64 existed and the image was successfully pushed. Untagged related manifest/attestation records can appear with Buildx provenance output. Do not delete them just because they are untagged without first understanding their relationship and retention needs.

8. Give EC2 permission to pull from ECR

EC2 must authenticate to the private ECR registry. The recommended AWS pattern is to attach an IAM role to the EC2 instance, rather than copying long-lived AWS access keys onto the server.

8.1 Create an IAM role for EC2

  1. In IAM, create a role for the trusted entity AWS service → EC2.
  2. Attach the AWS-managed policy AmazonEC2ContainerRegistryReadOnly.
  3. We named the role EC2-ECR-Pull-Role.
  4. Attach the role to the EC2 instance through EC2 → Instance → Actions → Security → Modify IAM role.

The read-only policy allows the instance to authenticate and retrieve images from ECR. It does not grant permission to push images or delete repositories.

8.2 Install AWS CLI on Ubuntu EC2

sudo apt update
sudo apt install -y awscli
aws --version

The EC2 instance initially did not have the AWS CLI installed, so we installed it. We did not run aws configure or add access keys. The instance role supplies temporary credentials automatically through the EC2 instance metadata service.

8.3 Verify the instance role

aws sts get-caller-identity

The returned ARN should contain an assumed-role identity, for example assumed-role/EC2-ECR-Pull-Role/.... This confirms the AWS CLI is using the instance role credentials.

9. Authenticate, pull and run the image on EC2

9.1 Authenticate Docker on EC2

aws ecr get-login-password --region ap-south-1 | \
sudo docker login --username AWS --password-stdin \
  404881858086.dkr.ecr.ap-south-1.amazonaws.com

We used sudo docker login because Docker commands on this Ubuntu instance were being run with sudo. Docker login credentials are stored for the Docker client context used by that command. Therefore, using sudo consistently for login and pull avoids logging in as one user and pulling as another.

9.2 Pull the tagged image

sudo docker pull \
  404881858086.dkr.ecr.ap-south-1.amazonaws.com/docker-spring-demo:1.0-amd64

sudo docker images

docker pull downloads the image from ECR to the EC2 host. It does not start the application. The image is now stored locally on EC2 and can be used to create a container.

9.3 Run the container

sudo docker run -d \
  --name docker-spring-demo \
  --restart unless-stopped \
  -p 8081:8080 \
  404881858086.dkr.ecr.ap-south-1.amazonaws.com/docker-spring-demo:1.0-amd64
OptionMeaning
-dRuns the container in detached/background mode.
--name docker-spring-demoAssigns a stable container name.
--restart unless-stoppedDocker restarts the container after daemon/host restart or process exit, unless an operator has explicitly stopped it. This is a basic restart policy, not a full high-availability strategy.
-p 8081:8080Publishes EC2 host port 8081 and forwards traffic to port 8080 inside the container.
ECR image URISpecifies the exact image and tag used to create the container.

9.4 Verify container and logs

sudo docker ps
sudo docker logs --tail 100 docker-spring-demo
sudo docker logs -f docker-spring-demo

Check that the container is Up, the port mapping shows 0.0.0.0:8081->8080/tcp, and the logs show Spring Boot/Tomcat started successfully on port 8080.

9.5 Open the EC2 Security Group port and test

In the EC2 instance's attached Security Group, add an inbound rule for TCP port 8081. For a learning test, restrict the source to your own public IP rather than opening it to the entire internet.

# Run from your Mac
curl -i http://EC2_PUBLIC_IP:8081/api/users

# Another endpoint
curl -i http://EC2_PUBLIC_IP:8081/api/users/1

Replace EC2_PUBLIC_IP with the current public IPv4 address of your instance. The first endpoint returned the three sample users, confirming the deployed application was reachable.

10. Troubleshooting issues we encountered

Docker CLI could not connect to Docker API/socket on Mac

Symptom: Docker reported it could not connect to ~/.docker/run/docker.sock.

Cause: Docker Desktop's engine was not running/ready. The Docker CLI is only the client; it needs the daemon.

Fix: Start Docker Desktop, wait for Engine running, then verify with:

docker info
docker ps

Port already allocated on EC2

Symptom: Docker failed with Bind for 0.0.0.0:9090 failed: port is already allocated.

Cause: An older container named hopeful_colden was already publishing EC2 host port 9090. Two containers cannot bind the same host IP/port combination.

Fix: We left the old container running and used host port 8081 for the new app. A failed container with the intended name was removed before retrying:

sudo docker rm docker-spring-demo
sudo docker run -d --name docker-spring-demo \
  --restart unless-stopped -p 8081:8080 \
  404881858086.dkr.ecr.ap-south-1.amazonaws.com/docker-spring-demo:1.0-amd64

ECR pull failed: no basic auth credentials

Symptom: no basic auth credentials during docker pull.

Cause: Docker was not logged in to the registry for the same user/context that was performing the pull. On this EC2 host, Docker was run with sudo.

Fix: Re-run ECR login with sudo docker login, then use sudo docker pull.

AWS CLI was not installed on EC2

Symptom: aws: command not found.

Fix: Install the CLI with sudo apt update and sudo apt install -y awscli. Do not put long-lived access keys on the EC2 server when an instance role is available.

Spring Boot Whitelabel Error Page

A Whitelabel page alone does not prove the Docker deployment is broken. It can mean the request reached Spring Boot but the path was not mapped, or the app returned an error. Test the exact endpoint, then inspect logs and make a request from inside the EC2 host:

sudo docker logs --tail 100 docker-spring-demo
curl -i http://localhost:8081/api/users

In our case, the new container had not started because the host port was occupied. After moving to port 8081 and successfully starting the container, the API worked.

Useful debugging sequence

sudo docker ps -a
sudo docker logs --tail 100 docker-spring-demo
sudo docker port docker-spring-demo
sudo docker inspect docker-spring-demo
curl -i http://localhost:8081/api/users

11. How this maps to a production CI/CD deployment

We performed each stage manually. A common production pattern automates most of it:

Developer pushes code→CI pipeline tests/builds→Docker image build→Push to ECR→Deploy workload
  1. Source control: a developer merges code into a Git branch.
  2. CI: GitHub Actions, Jenkins or another runner compiles the Java app, runs tests and packages the JAR.
  3. Image build: the pipeline builds a Docker image, ideally with a unique immutable tag such as a commit SHA or release version.
  4. Registry: the pipeline authenticates to ECR and pushes the image.
  5. Deployment: a deployment mechanism updates the EC2 service, ECS service, or Kubernetes workload to use the new image.
  6. Verification/rollback: health checks and monitoring verify the release; a previous known-good image can be redeployed if necessary.

What is different from a mature production setup?

  • Use a CI/CD pipeline instead of manually building and pushing from a developer laptop.
  • Use immutable release identifiers (for example, commit SHA) rather than relying only on a mutable tag like latest.
  • Use a load balancer, multiple instances/tasks, health checks and a rolling or blue/green deployment strategy for availability.
  • Keep secrets out of images and source control; inject them securely at runtime.
  • Use logs, metrics, alarms, tracing and vulnerability scanning.
  • Apply least-privilege IAM roles: CI needs push permissions; EC2 runtime needs pull permissions only.
  • Consider ECS or EKS for managed orchestration when the system's complexity and scale justify it.
Production caution: A single EC2 instance with one container and a public port is a learning deployment, not a highly available production architecture. The --restart policy helps restart a process but does not protect against an EC2/AZ failure.
